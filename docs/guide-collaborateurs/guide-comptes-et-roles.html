Aux membres du groupe qui découvrent le projet. Il ne suppose aucune connaissance préalable du code : lisez-le dans l'ordre, puis gardez la section 8 (« Problèmes fréquents ») sous la main.

Chaque collaborateur installe sa propre instance, avec des mots de passe générés au hasard pour lui seul. Les vôtres s'affichent dans votre terminal (section 1.3). Ne les envoyez jamais par message et ne les copiez pas dans un fichier du dépôt.

1. Démarrer l'application

1.1 Première installation (une seule fois)

Les prérequis (PHP 8.1+, MySQL 8.4, Python 3.10+) sont détaillés dans le README.md du dépôt. Ensuite :

git clone https://github.com/bymelwine/securepayroll.git
cd securepayroll
python3 bin/init-local.py          # quelques minutes ; crée le dossier privé .local/

L'installation crée une base privée dans le dossier .local/ de votre copie du projet. Elle ne touche pas au MySQL éventuellement installé sur votre machine, et elle n'est pas accessible par le réseau : seulement par un fichier spécial, le socket .local/mysql.sock.

1.2 Lancer et arrêter

cd securepayroll
python3 bin/init-local.py serve
# ↑ démarre MySQL puis l'application ; laisser ce terminal ouvert

Ouvrir ensuite http://127.0.0.1:8080/login dans le navigateur de la même machine.

# Pour arrêter : Ctrl+C dans le terminal (arrête l'application), puis :
python3 bin/init-local.py stop     # arrête MySQL ; les données sont conservées
python3 bin/init-local.py status   # MySQL est-il en marche ?

1.3 Trouver ses identifiants

python3 bin/init-local.py credentials

La sortie a cette forme (valeurs inventées pour l'exemple) :

svc_php : Qm4x...                  ← compte interne de l'application : PAS un login web
hr.demo : Xk3_9fQ-pL0vTzr2Hq8sWb1YcN6uAe7D   ← identifiant = hr.demo
finance.demo : ...
...
Comptes MySQL d'exploitation (socket .../.local/mysql.sock) :
  dba_ops : ...                     ← pour accéder à la base (section 7)
  backup_ops : ...
  audit_ops : ...
« Les mots de passe ont l'air chiffrés » : non, ils sont en clair

Ce sont de vrais mots de passe, générés au hasard : 32 caractères faits de lettres, de chiffres, de - et de _. L'identifiant est ce qui précède « : », le mot de passe ce qui suit (sans l'espace). Un mot de passe peut commencer par -.

Copiez-collez-les (sélection à la souris, puis Ctrl+Maj+C dans le terminal) : les taper à la main mène vite au blocage du compte.

5 mauvais mots de passe = compte bloqué 15 minutes

C'est une protection contre les attaques par force brute. Seul le compte concerné est bloqué ; les autres restent utilisables. Pour débloquer plus tôt pendant une démonstration : ls .local/runtime/login-account-*.json, puis supprimer ces fichiers.

2. Compte ou rôle : la différence

Ce sont deux notions distinctes, qu'on confond souvent :

CompteRôle
Question« Qui es-tu ? »« Qu'as-tu le droit de faire ? »
ContenuUne identité et un moyen de la prouver : identifiant + mot de passeUn ensemble de permissions. Pas de mot de passe
Sert àS'authentifier (prouver son identité)Autoriser (ouvrir ou refuser une action)
AnalogieVotre badge nominatifLa liste des portes que ce badge ouvre

Personne ne se connecte « en tant que rôle » : on se connecte avec un compte, auquel on a attribué un ou plusieurs rôles. Dans SecurePayroll, la chaîne complète est :

Personneun salariéemployees
→
Compteidentifiant + mot de passeaccounts
→
Attributiondatée, motivée, révocablerole_assignments
→
Rôleex. Employeeroles
→
Permissionsex. voir ses bulletinspermissions

Exemple réel : Nadia TRAORE (personne) se connecte avec le compte employee.demo ; une attribution lui donne le rôle Employee, qui contient la permission payslip.self (voir ses propres bulletins).

Pourquoi séparer les deux
  • On change les droits de quelqu'un sans toucher à son mot de passe (changement de poste, absence, départ).
  • On modifie un rôle une seule fois pour toutes les personnes qui l'ont.
  • On garde l'historique : qui a donné quel rôle, à qui, quand et pourquoi. Il ne peut pas être effacé.

Données personnelles

Aucun rôle n'accède aujourd'hui aux données personnelles (CIN, numéro CNSS, RIB). Elles sont stockées, mais aucune fonction de l'application ne les lit encore.

4. Qui peut assumer un rôle

N'importe quel salarié qui possède un compte, à condition que l'administrateur applicatif lui attribue le rôle, avec un motif obligatoire. Quatre règles, vérifiées par la base de données, encadrent ces attributions :

  1. Pas d'auto-attribution : l'administrateur ne peut pas se donner un rôle à lui-même.
  2. Pas de cumul : une personne a au plus un rôle parmi RH, Finance, Paie, Administrateur et Auditeur. Seul le rôle Employee peut s'y ajouter.
  3. Repli de sécurité : si un cumul existait malgré tout, la personne ne garderait que ses droits de salarié.
  4. Attributions datées : elles peuvent expirer, et une révocation prend effet dès la page suivante, sans attendre une nouvelle connexion.

Ajouter un nouveau salarié (embauche)

  1. La RH (hr.demo) ouvre Ajouter un employé et saisit le matricule, le prénom, le nom et l'adresse e-mail personnelle du salarié. Aucune donnée bancaire n'est demandée.
  2. L'application crée en une seule opération le salarié, son compte prenom.nom@securepayroll.ma (prenom.nom2@… en cas d'homonyme) et son rôle Employee. La RH voit l'identifiant créé, jamais le mot de passe.
  3. Un mot de passe temporaire, valable 72 heures, est envoyé à l'adresse personnelle. En local, il n'y a pas de vrai serveur de messagerie : le message est déposé dans une boîte d'envoi privée, à lire dans un terminal avec python3 bin/init-local.py outbox.
  4. À sa première connexion, le salarié ne voit qu'une page : Activez votre compte. Il saisit le mot de passe temporaire, puis son propre mot de passe (12 caractères au moins, sans son nom ni son prénom). Le compte devient alors actif.

Un autre rôle (RH, Finance…) ne s'obtient pas à l'embauche : il reste attribué par l'administrateur, comme ci-dessus. Tout utilisateur peut aussi changer son mot de passe à tout moment, depuis le menu Mot de passe ; ses autres sessions sont alors fermées. La RH écrit l'adresse personnelle, mais ne peut plus la relire : elle n'en a pas besoin.

5. Les comptes MySQL et les rôles MySQL

Tout ce qui précède concerne l'application web. La base MySQL a ses propres comptes et ses propres rôles, sur le même principe : un compte pour se connecter, des rôles pour les droits.

5.1 Les comptes MySQL

CompteUtilisé parCe qu'il peut faire
rootUn humain, rarementTout, y compris créer des comptes et donner des droits. Réservé à ces opérations.
dba_opsL'administrateur de la baseTout sur la base secure_payroll (tables, procédures, données). Ne peut ni créer de compte ni donner de droits.
backup_opsLes sauvegardesLire toute la base pour l'exporter. Aucune écriture.
audit_opsUn auditeur SQLLire les historiques et les attributions de rôles. Ni montants, ni empreintes de mots de passe, ni données personnelles.
svc_phpL'application PHP, jamais un humainRien directement. À chaque page, il active les rôles MySQL de l'utilisateur web connecté (section 6).
5 comptes *_ownerPersonne : verrouillésIls « possèdent » les procédures stockées, qui s'exécutent avec leurs droits. Personne ne peut se connecter avec eux.
Comptes humains : verrouillage après 5 échecs

dba_ops et audit_ops sont bloqués une journée après 5 mauvais mots de passe, et leur mot de passe expire tous les 90 jours. root peut les débloquer : ALTER USER 'dba_ops'@'localhost' ACCOUNT UNLOCK;

5.2 Les 12 « utilisateurs » sp_* sont des rôles, pas des comptes

Dans la liste des utilisateurs MySQL (par exemple dans Workbench), vous verrez 12 entrées commençant par sp_. Ce sont des rôles MySQL. MySQL les range dans la même table que les comptes, verrouillés et sans mot de passe, ce qui prête à confusion.

Rôle MySQLÀ quoi il sert
sp_sessionLire l'identité et les rôles de l'utilisateur, à chaque page
sp_loginLire l'empreinte du mot de passe, seulement pendant la connexion
sp_passwordChanger un mot de passe, seulement le temps de ce changement
sp_employee, sp_hr_manager, sp_finance_manager, sp_payroll_manager, sp_application_administrator, sp_security_auditorUn par rôle de l'application : les droits MySQL exacts dont ce rôle a besoin, et rien de plus
sp_dba, sp_backup, sp_db_auditorLes droits des comptes dba_ops, backup_ops et audit_ops

6. Comment les deux niveaux se rejoignent

Toutes les pages de l'application parlent à MySQL avec le même compte, svc_php. Mais à chaque page, celui-ci n'active que les rôles MySQL correspondant à l'utilisateur web connecté :

Camille se connecte avec hr.demo
Applicationmot de passe vérifié ; rôle lu : HR Manager
MySQLsvc_php active sp_session + sp_hr_manager
Salaireslisibles
Nadia se connecte avec employee.demo
Applicationmot de passe vérifié ; rôle lu : Employee
MySQLsvc_php active sp_session + sp_employee
Salairesrefusés par MySQL

Conséquence : même si une page ouverte à Nadia contenait une faille (une injection SQL, par exemple), la requête malveillante s'exécuterait avec les seuls droits de Nadia. MySQL refuserait la lecture des salaires. C'est le principe du moindre privilège, et c'est ce que la phase d'attaque du projet (phases 4 et 5) démontrera.

7. Accéder à la base de données

L'application doit être lancée (serve), ou au moins MySQL (python3 bin/init-local.py start). Utilisez de préférence dba_ops pour explorer, audit_ops pour voir le moindre privilège en action, et root seulement pour gérer les comptes et les droits.

7.1 En ligne de commande

cd securepayroll
mysql --no-defaults --socket=.local/mysql.sock -u dba_ops -p secure_payroll
# coller le mot de passe de dba_ops affiché par « credentials »

Quelques requêtes pour commencer :

SHOW TABLES;
SELECT CURRENT_USER(), CURRENT_ROLE();  -- qui suis-je ? rôles actifs ?
SHOW GRANTS;                            -- mes droits effectifs
SELECT login, LEFT(password_hash, 31) FROM accounts;
-- ↑ empreintes Argon2id des mots de passe (visible par dba_ops)

Mot de passe de root (il n'est pas affiché par credentials), à lancer dans un terminal :

python3 -c "import json; print(json.load(open('.local/admin.json'))['password'])"

7.2 Avec MySQL Workbench

  1. Dans un terminal, afficher le chemin complet du socket : realpath .local/mysql.sock
  2. Dans Workbench, cliquer sur + à côté de « MySQL Connections ».
  3. Connection Method : Local Socket/Pipe.
  4. Socket/Pipe Path : le chemin obtenu à l'étape 1.
  5. Username : dba_ops (ou audit_ops) ; Default Schema : secure_payroll.
  6. Test Connection, coller le mot de passe sans l'enregistrer. Si un avertissement de version apparaît (Workbench 8.0, serveur 8.4), choisir Continue Anyway.

7.3 Expérience à faire : voir le moindre privilège

SELECT amount FROM settlement_ledger;
  • Connecté avec dba_ops : la requête renvoie les montants payés.
  • Connecté avec audit_ops : MySQL la refuse (erreur 1143), car ce compte n'a pas le droit de lire les montants.
Deux pièges à éviter
  • Toujours --no-defaults en ligne de commande : sinon mysql peut lire la configuration d'un autre MySQL installé sur la machine.
  • Ne pas se connecter à localhost:3306 : c'est le MySQL du système (s'il existe), pas la base du projet. La base SecurePayroll n'est joignable que par le socket.

8. Problèmes fréquents

SymptômeCause et solution
Les mots de passe de credentials « semblent chiffrés »Ils sont en clair, simplement aléatoires. Identifiant avant « : », mot de passe après (section 1.3).
« Trop de tentatives. Réessayez dans quinze minutes. »5 échecs sur ce compte. Attendre 15 minutes, ou supprimer .local/runtime/login-account-*.json. Les autres comptes fonctionnent.
« Identifiant ou mot de passe incorrect » avec le bon mot de passeEspace copié en trop, ou login svc_php utilisé (ce n'est pas un compte web). Le message est volontairement le même dans tous les cas, pour ne pas révéler quels comptes existent.
La page ne s'ouvre passerve n'est pas lancé, ou le navigateur n'est pas sur la même machine : l'application n'écoute que sur 127.0.0.1.
Erreur 503 sur toutes les pagesInstance installée avant la phase 2. La mettre de côté puis réinstaller : python3 bin/init-local.py stop, puis mv .local .local.avant-phase2, puis python3 bin/init-local.py. Rien n'est supprimé.
Erreur 503 après la mise à jour « embauche »Instance installée avant cette fonctionnalité. La mettre à niveau, sans perte : python3 bin/init-local.py upgrade.
« Votre mot de passe temporaire a expiré »Plus de 72 heures depuis l'embauche. Le compte n'a jamais été activé ; il faut une nouvelle invitation (à ce stade : réinstaller l'instance de démonstration ou recréer le salarié avec un autre matricule).
mysql : « Access denied » ou « account is locked »Mauvais mot de passe, ou 5 échecs sur dba_ops/audit_ops : déblocage par root (section 5.1).
audit_ops : « SELECT command denied » (1142 ou 1143)Ce n'est pas une panne : ce compte n'a volontairement pas accès aux montants ni aux données personnelles.
